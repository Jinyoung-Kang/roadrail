# ADR-013 어디서 → 어디로: 전국 임의 지점 선택

- 상태: 채택 (2026-09-24)
- 배경: 미리 정한 8개 길 안에서만 고르게 하면 쓸모가 제한된다. 사용자는 전국 어디서든 출발·도착을 검색으로 고르고 싶다.
- 데이터 원천별 가능성 (실측)

| 원천 | 임의 지점 | 방법 |
|---|---|---|
| 자동차 | 가능 | 카카오 미래 운행 정보 길찾기 — 두 좌표 · 출발 시각 → 소요시간 · 경로 좌표 (전주→서울 1,813점을 400점으로 줄임) |
| 기차 | 가능 | 전국 전 열차 운행정보를 이미 보관(ADR-003). 역 276개 좌표를 카카오 키워드로 보정(`station_geocode`, 276/276). 임의 역 쌍은 SQL 함수 `rail.od_trips` |
| 날씨 · 대기 | 가능 | 격자·시도를 좌표로 계산해 수집된 값이 있으면 DB, 없으면 조회 시점 호출 (Redis 캐시 · 공유 예산) |
| 고속도로 실측 추이 | **길 8개만** | 구간 체인 수집은 호출 예산이 드는 상주 작업(ADR-008). 임의 지점이 수집 중인 길과 30km 안에서 겹치면 실측(평소 대비 %)을 근거로 덧붙임 |

- 결정:
  1. 검색 `GET /places/search` — 행정구역(카카오 주소) → 운행 중인 기차역(DB) → 장소(카카오 키워드).
  2. 판단 `GET /trip` — 출발·도착 반경 40km 안의 운행 역 최대 4곳씩 조합해 '역까지 + 대기 + 탑승 + 역에서'가 가장 작은 직통 열차 (환승 제외, 그날 없으면 다음 날 첫차). 역까지·역에서 시간은 직선거리 × 1.3 ÷ 25km/h(최소 5분)로 추정하고 화면에 '(추정)' 표시.
  3. 철도 분석은 임의 역 쌍 (`/rail/od/*`). 정시성 규칙 P-i1 은 SQL 함수 한 곳에만 두고, Python 기준 구현과 같은 값을 내는지 통합 테스트로 고정 (`test_od_trips_matches_python_reference`). 길별로 매일 미리 계산하던 `rail.corridor_trip` 은 삭제(V6).
  4. api 가 외부 API 를 직접 부르게 되므로 collector 와 **같은 Redis 예산 키 · 같은 Lua** 로 차감(`QuotaGuard`). 카카오는 길찾기(`KAKAO`)와 검색(`KAKAO_LOCAL`, 공식 10만/일)으로 예산을 나눔.
  5. 응답 예산(NFR-03): 자동차·기차·양쪽 환경을 가상 스레드로 병렬 실행하고 외부 대기는 하나의 마감(0.75초)을 공유. 늦은 값은 `pending` 으로 알려 화면이 1.5초 뒤 다시 부르고, 서버는 조회를 계속해 캐시를 채운다.
- 결과: 캐시 미적중 0.69~0.77초 · 두 번째 16~130ms (강릉→부산, 목포→대구, 충주→광주 실측).
- 한계: 환승 경로 없음 · 역 접근 시간은 추정 · 고속도로 실측은 수집 중인 길만.
