# ADR-017 쿼리 성능 — JIT 끄기 · 역 쌍 해시 조인 · 한 번 계산 · 결과 캐시

- 상태: 채택 (2026-09-25)
- 배경: 철도 분석 화면(90일, 요청 3개 동시) p50 1,972ms · 날짜별 운행 1,508ms. 다른 API 는 6~110ms.

## 진단 (EXPLAIN ANALYZE)

| 관찰 | 수치 |
|---|---|
| `rail.od_trips` 서울→부산 90일 | 574ms — 그중 첫 노드 시작에 **464ms** (6월 파티션 단독 조회는 0.8ms) |
| 같은 쿼리 `SET jit = off` | **94ms** → 시작 지연의 정체는 쿼리마다 하는 JIT 컴파일 |
| 출발역 행마다 `LATERAL` 로 뒤쪽 정차를 인덱스로 훑는 짝짓기 | 16,168회 인덱스 탐색 |
| 정시율 요청 1건 | `od_trips` 를 두 번(묶음별 + 요약) → 화면 1번에 6번 |
| 날짜별 운행 | 120일 `od_trips` 두 번(날짜 목록 + 기본 날짜) |

## 결정

1. **JIT 끄기** (V14, `ALTER DATABASE … SET jit = off`) — 이 서비스의 쿼리는 수만 행 규모로 짧고 자주 불려 컴파일 비용을 회수하지 못한다. 마이그레이션으로 두어 운영 · Testcontainers · 수집기 테스트 DB 가 같게.
2. **해시 조인** (V14) — 출발역 행 × 도착역 행을 (운행일, 열차)로 조인, `DISTINCT ON` 으로 출발역 다음 첫 도착역 정차 하나. 세 역 쌍에서 V11 결과와 **행 단위로 같음**(EXCEPT ALL 0행) 확인 후 교체.
3. **한 번 계산** — 정시율은 `GROUP BY GROUPING SETS ((k), ())` 로 묶음별 행과 전체 요약 · 분포를 한 쿼리에. 날짜별 운행은 날짜별 (운행 수, 확인 수) 한 번으로 목록과 기본 날짜를 함께.
4. **결과 캐시 10분** (Redis) — 과거 기간 결과는 새 운행 자료(하루 세 번)나 시간표가 들어오기 전까지 같다. TAGO 시간표를 받는 중인 응답은 캐시하지 않는다.

| 요청 (p50) | 전 | 후 · 캐시 없음 | 후 · 캐시 적중 |

## 버린 대안

- 정시성 결과를 미리 계산해 두는 물질화 뷰 — 역 쌍이 약 7만 가지라 전부 미리 계산할 수 없고, 시간표(TAGO)가 늦게 채워지면 갱신이 복잡하다. 요청 시 계산 + 짧은 캐시로 충분.
- `jit_above_cost` 만 올리기 — 효과는 같지만 기준값을 데이터 크기에 맞춰 계속 조정해야 한다.
