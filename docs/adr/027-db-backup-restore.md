# ADR-027 DB 백업 · 복원 — pg_dump 사용자 지정 형식 · 별도 DB 리허설 · 이름 바꿔 끼우기

- 상태: 채택 (2026-10-04)
- 배경: QA([보고서](../qa/2026-10-04-qa-report.md) 5절 개선 2)에서 백업 · 복원 절차가 없었다. 수집한 시계열은 원천이 하루 · 몇 시간 뒤면
  다시 주지 않는 것이 많아(도로공사 꼬리 커서 · 문자 안내 · UTIC, VERIFICATION 79번) 볼륨을 잃으면 되살릴 수 없다. QA 때 손으로
  `pg_dump` → `pg_restore` 를 해 보니 232MB 가 11초에 복원됐다.
- 원칙: 새 의존성 · 새 서비스 없이 db 컨테이너의 `pg_dump` · `pg_restore`(서버와 같은 16) 로. 지금 DB 를 바꾸는 일은 묻고, 되돌릴 수 있게.

## 결정

1. **형식은 `pg_dump -Fc`(사용자 지정 · 압축).** 표 하나만 되살리거나(`pg_restore -t`) 목차를 읽어 확인할 수 있다. 파일은 `backups/`(저장소 밖) —
   데이터가 그대로 들어 있으니 커밋하지 않는다(키는 없다: 호출 기록은 마스킹된 값만).
2. **저장 전에 확인한다.** `.part` 로 받은 뒤 `pg_restore --list` 로 표 데이터가 있는지 보고서야 이름을 붙인다. 보관은 최근 `KEEP=7` 개.
3. **복원은 먼저 별도 DB 에.** `make restore-check` 는 `roadrail_restore` 에 복원해 표마다 행 수를 지금 DB 와 나란히 보인다 — 백업이 실제로
   되살아나는지 정기적으로 확인하는 리허설이자, 교체의 첫 단계.
4. **교체는 이름 바꿔 끼우기.** `make restore` 는 확인 질문(비대화형은 `CONFIRM=roadrail`) → 지금 DB 자동 백업(`backups/before-restore`, 3개) →
   별도 DB 에 복원 → api · collector 정지 → `ALTER DATABASE … RENAME` 두 번 → 서비스 시작 → 옛 DB 삭제. 서비스가 멈추는 것은 이름 바꾸기 동안뿐이고,
   복원이 실패하면 지금 DB 는 그대로다. 도중에 실패해도 멈춘 서비스는 다시 띄운다.
   - 하지 않은 것: `pg_restore --clean` 으로 지금 DB 위에 덮어쓰기(실패하면 반쯤 지워진 DB 가 남는다), 수집기 안의 자동 백업 작업
     (수집기 이미지에 `pg_dump` 가 없고, 백업 파일은 호스트에 있어야 볼륨을 잃어도 남는다 — 정기 실행은 호스트의 크론에 맡긴다).

## 결과

- 개발 DB 실측: 백업 3.6초 · 16MB(표 데이터 52개), 리허설 복원 6초 · 표 29개 · 145만 행이 지금 DB 와 같음.
- 교체는 일회용 DB(`DB_NAME=roadrail_scratch`)로 확인 — 지운 표가 백업 값으로 돌아오고, 교체 전 자동 백업 · 옛 DB 정리, 확인을 거절하면 아무것도 하지 않음.
  실제 `roadrail` 교체(서비스 정지 · 시작 포함)는 사용자 데이터라 돌려 보지 않았다.
